# `rs-config` 设计与实现评审（2026-07-11）

## 结论

`rs-config` 的核心方向值得保留，尤其是 `ConfigReader` 与 `ConfigPrefixView` 已在真实下游中证明有效：`rs-http` 通过泛型 `ConfigReader`、相对 key 与 prefix view 组合加载大量嵌套选项，`rs-retry`、`rs-mime` 也复用了同一读取模型。

当前问题集中在“配置存在性、typed/text 转换、结构化反序列化”三个语义没有统一。建议先修正这些基础契约，再决定 source、serde 和 legacy API 的稳定边界；不建议继续扩大 API 面。

本评审中没有发现 P0。

## 做得好的部分

- `ConfigReader` 让消费者依赖只读接口，而不是具体 `Config` 所有权；prefix view 的相对 key 语义非常适合组合式配置。
- 读取错误保留 key 上下文，final property 防止被无意覆盖，source 加载具有较好的事务性。
- 环境变量替换默认回退关闭，避免无意读取外部环境；多 source 与 feature 组合已有较完整测试矩阵。
- `ReadPolicy` 把读取策略集中在配置入口，整体方向正确。

## 需要优先修复的契约问题

### P1：`Vec<T>` 读取经由 String 中转，破坏 typed value 和 rich type

`src/from/from_config.rs` 中的 `impl<T> FromConfig for Vec<T>` 先执行 `to_list_with::<String>`，再将每个元素重新包装为 `MultiValues::String`。对于 char、日期时间、大数、StringMap 等不支持 String 通用转换的目标类型，这会导致本可读取的 typed value 失败；Duration 列表还会在中转时丢失亚毫秒精度。

建议逐元素保留原始 variant，不要把 `String` 当作通用中间表示。字符串 source 的解析能力应由清晰、可测试的文本 codec 提供。

### P1：显式空列表与缺失配置被混为一谈

`src/from/helpers.rs` 中 `is_effectively_missing_by` 会将任何 `property.is_empty()` 判为 missing。由于 `MultiValues::String(vec![])` 也是 empty，显式空数组会在不同 API 中表现矛盾：list getter 返回空列表，optional getter 返回 `None`，带默认值 getter 返回默认值，而结构化反序列化可得到 `Some(vec![])`。

这已影响带默认列表的下游配置：用户无法通过空数组表达“清空默认值”。应只将 typed null/`MultiValues::Empty` 视为缺失，typed empty collection 则是已存在的空值。

### P1：`Config::deserialize` 的支持面与真实投影不一致

`ConfigValueDeserializer` 缺少 `i128/u128` 方法；同时 JSON 投影会把 Duration、大数、日期时间和 128 位整数写成字符串。结果是公开的 `Config::deserialize` 无法正确处理一部分已支持的 `MultiValues` 类型。

建议为每个 `DataType` 明确结构化 Serde 表达，并增加全 variant round-trip；在修复前，应把该 API 视为实验能力，而非与 `get<T>` 同等稳定的入口。

## 需要在下个阶段处理的问题

### P2：Config 的 derive Deserialize 可绕过内部不变量

`Config` 的 map key 与 `Property::name` 应一致，`insert_property` 会验证该约束；但直接 derive `Deserialize` 可以构造二者不一致的对象。建议改用 DTO + 自定义反序列化校验，或去除冗余名称字段。

### P2：错误模型与公开 enum 演进成本偏高

上游 `DataConversionError`、`ValueError` 会被压平为文本，丢失 source 和安全分类。`ConfigError` 又是可被下游穷举 match 的公开 enum，新增 variant 会造成协调式破坏。

建议保留结构化 source、默认脱敏原始配置值；在下一不兼容版本使用 `#[non_exhaustive]` 或稳定的 error kind/accessor 模式。

### P2：`rich-types` feature 没有达到依赖裁剪目标

即使关闭默认 feature，仍会通过 `qubit-datatype`、`qubit-value` 带入 Chrono、URL、BigInt、BigDecimal 等依赖。应在三个基础层统一 feature 设计；如果 enum 条件编译会破坏 wire 稳定性，应优先拆分 core/runtime adapter，而不是仅隐藏 API。

### P2：核心 reader 成功，但公开表面需要收敛

`ConfigReader` 的泛型 API 非 object-safe，这对当前 `R: ConfigReader + ?Sized` 使用方式没有问题；如果未来确实需要 `dyn ConfigReader`，再拆分 object-safe raw reader 与泛型 extension trait。当前没有必要为此重做已验证的泛型接口。

`Configured/Configurable`、部分 source/serde 路径在当前 `rs-*` 生产代码中缺少实际消费者。应优先标记实验性或 feature 化，而不是继续增加稳定承诺。

## 建议的演进顺序

1. 修复 typed list、explicit empty 与 missing/null 的语义，并加入跨来源契约测试。
2. 让数值和布尔转换默认 exact，消除 TOML/YAML 与 env/properties 的行为差异。
3. 为结构化反序列化定义完整、版本化的 DataType 映射。
4. 收敛错误模型和内部反序列化不变量，再处理 feature 与 API 面。
5. 建立使用本地 path patch 的跨仓 CI，保证下游测试运行的是当前源码而不是已发布版本。

## 验证记录

本轮执行 `cargo test --all-features --all-targets --quiet`，776 个测试通过；`cargo clippy --all-features --all-targets -- -D warnings` 通过。以本地 path patch 运行 `rs-retry`、`rs-http`、`rs-mime` 等下游测试均通过。现有测试未覆盖 typed empty/missing 分歧、rich type 结构化反序列化和跨来源 exactness。
